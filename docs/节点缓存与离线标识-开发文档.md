## 一、现状梳理

> 本节是**实施前**（2026-10-02 方案评审时）的现状快照，用于对照"改了什么"；
> 其中描述的行为与代码行号可能已随实现变化，判断当前行为请以代码与文末「实施落地与原方案的差异」为准。

### 1.1 缓存体系总览

全部本地缓存集中在 `SessionStore`（SharedPreferences `slte_session`，加密存储），无数据库。TTL 统一定义在 `ServerRepository.CachePolicy`：

| 缓存 | 存储 | 键 | TTL | 失效/清空时机 |
|---|---|---|---|---|
| 登录态（auth/email/token） | SessionStore | `auth_data` 等 | 无（登录期永久） | 退出登录 |
| 订阅信息 SubscribeInfo | SessionStore | `subscribe_info` | 30 秒 | 每次强刷覆盖 |
| 用户信息 User | SessionStore | `user_info` | 30 秒 | 每次强刷覆盖 |
| **节点列表** | SessionStore | `server_nodes`（JSON 数组） | **30 分钟** | 更新订阅强刷；网络失败时无 TTL 兜底继续用旧值（`ServerRepository.fetchServers` recover 分支） |
| **节点延迟（测速）** | SessionStore | `speed_results`（`name→ms` JSON） | **6 小时** | **订阅更新即清空**（`clearSpeedResults`）；退出登录清空 |
| 远程配置 | RemoteConfigStore | 含 `fetchedAt` 时间戳 | 多源并发拉取、按 `config_version` 择优 | 启动/到期重拉 |
| 内核组选择持久化 | 内核 cache.db | 组名→节点名 | — | **被显式禁用**（见 §2.2） |
| Override(Persist) | 内核 home 下 `override.json` | 目前只存代理模式 `mode` | 文件级永久 | 无人在节点选择上使用它 |

几个关键事实：

- **测速缓存只存"成功值"**：`NodeLatency.kt:56` 过滤掉 `DELAY_TIMEOUT`，超时/失败从不落盘。冷启动进节点页，未重测的失败节点显示为无值（`--`），而不是"超时"。
- **延迟是单一 Int 哨兵模型**：`Constants.DELAY_TIMEOUT = 999`，`normalizeDelay` 把内核返回的 `<=0 或 >=65535` 一律压成 999。mihomo 对"连不上"和"连上但超时"都报失败（delay=0），**当前数据模型无法区分**。
- **国旗没有独立缓存**：普通节点行的国旗从**面板下发的节点名**实时提取（`NodeCountry.extractCountryCode`：关键词表→国旗 emoji→ISO 码，兜底 `XX`），随节点列表缓存间接持久化；"自动选择/故障转移"两行没有自己的名字，国旗只能靠"内核当前成员名 → 节点列表反查"（`ServerViewModel.countryOf`），**内核不在线或匹配失败就永远是灰色地球占位**（`FlagPlaceholder.NeutralFlag`），且没有任何持久化。
- 首页"服务器"一行只显示节点名文本（`watchLiveSelection` 1.5s 轮询内核），不显示国旗；首页国旗只有"当前IP"行（IP 地理库，与此无关）。

### 1.2 节点选择链路（现状）

```
切换：ServerViewModel.selectNode(id)
      ├─ 0  → KernelProxy.selectAuto()     → patchSelector(选择组, URLTest组)
      ├─ -1 → KernelProxy.selectFallback() → patchSelector(选择组, Fallback组)
      └─ id → KernelProxy.selectNode(name) → NodeNameResolver.resolve → patchSelector + 回读校验
      全部只写内核运行时状态，不落任何盘。

读取：KernelProxy.serverInfo() → 内核 selector 组的 now → 反推 AUTO/FALLBACK/MANUAL
      ServerViewModel.refreshSpecialNodes() → selectedNodeIdOf() → 勾选状态
```

**重启后回到"自动选择"的完整因果链**（已逐行核实）：

1. `kernel-core/src/main/golang/native/config/process.go:84`：`cfg.Profile.StoreSelected = false` —— mihomo 上游默认是 `true`（会写 cache.db 恢复组选择），SLTE 补丁链**显式关掉了它**，且无注释说明原因。
2. 内核启动加载配置后，Selector 组回落到**配置里的第一个成员**。分组来自机场订阅下发的 `proxy-groups`（应用侧 `SanitizerInjector` 只注入健康检查参数，不建组），面板把"自动选择"组排在节点前面 → 默认即"自动选择"。
3. 应用侧**也没有任何持久化**：`selectedNodeId` 只活在 `ServerData`（内存 StateFlow），`SessionStore` 无对应键；`ServerData` 默认值就是 `0`（自动选择）。
4. 连接建立后 `MainViewModel.startAutoSelectionAndTest()` → `refreshSelectionAndMeasure()` 读到内核已被重置的 AUTO，还会"再应用一次"，把状态钉死。

### 1.3 现有但未用上的持久化通道

内核提供 Override 机制：`override.json`（Persist 槽，**文件级持久化**）在每次配置加载时被 `process.go:patchOverride` 直接解码进 RawConfig。app 目前只用它存代理模式（`KernelProxy.setProxyMode` / `ensurePersistedMode`，含"内核未就绪先存本地、就绪后同步"的完整范式）。但 Kotlin 侧 `ConfigurationOverride` 模型**没有 selected（组→节点）字段**，Go 侧 RawConfig 也没有对应应用点——这条通道目前承载不了节点选择。

## 二、问题一：重启后手选节点回到"自动选择"，合理吗？

### 2.1 结论

**不合理，建议改。** 理由：

- 用户显式做出的选择被**静默**覆盖，违背最小惊讶；同类产品（mihomo 生态各面板/客户端）默认都会记住选择。
- "默认自动选择"本身是合理的**兜底**——但只应作为**恢复失败时的降级**（节点改名/被删），不应无条件覆盖用户选择。

### 2.2 方案对比

| 方案 | 改动 | 优点 | 缺点 |
|---|---|---|---|
| **A. 内核层**：`process.go:84` 改回 `StoreSelected = true`，重编 `libclash.so` | Go 一行 + 重编内核 | mihomo 原生机制，配置加载瞬间恢复，无时间窗；选择由 cache.db（home 目录）持久化 | 需要重编 `.so`（README 有流程，无需 NDK）；cache.db 按节点名匹配，订阅改名后恢复失败 → 回落首个成员（=自动选择，恰好是想要的兜底） |
| **B. 应用层**：SessionStore 新增 `selected_selection`（type + kernelNodeName），连接建立后重放 | 纯 Kotlin | 不依赖内核重编，随下个版本立即生效；UI 勾选可在内核上报前先正确显示；可配合 `NodeNameResolver` 做改名模糊匹配 | 内核启动 → 重放之间有几秒走默认（自动选择）的窗口 |

**推荐 A + B 都做**：B 先行（见 §5 分期），A 排进下一次内核重编一起出。两层语义一致：应用层是 UI 真值来源，内核层保证流量路径无窗口期。

### 2.3 设计细节（方案 B）

- 存储：`SessionStore` 新增 `KEY_SELECTION = {"type":"MANUAL|AUTO|FALLBACK","node":"<kernel节点名>","savedAt":...}`。
- 写入点：`selectNode/selectAuto/selectFallback` 成功（现有回读校验通过）后落盘。
- 恢复点：连接建立流程在 `refreshSelectionAndMeasure()` **之前**插入 `ensurePersistedSelection()`（完全复刻 `ensurePersistedMode` 的模式）：
  - MANUAL → `selectNode(savedNode)`；解析失败（节点已改名/删除）→ 清存储、落回 AUTO，并打日志；
  - AUTO/FALLBACK → `applySelection(type)`；
  - 订阅更新（`SubscriptionUpdater`）成功后：节点名可能变化，恢复动作照跑，失败自动降级 AUTO。
- 边界：恢复只在**连接建立/订阅更新**两个时机做，节点页进入时仍以内核实时状态为准（现状不变），避免双写打架。

## 三、问题二：自动选择/故障转移的国旗与缓存

### 3.1 现状痛点

内核未连接、未完成首轮刷新、或成员名匹配不上时，两行国旗显示灰色地球，且没有任何"上次是谁"的记忆——这正是"没有国旗缓存"的体感。

### 3.2 方案

`SessionStore` 新增两个缓存键（随节点列表缓存同生命周期，订阅更新/退出登录时清空）：

```
special_node_auto     = {"kernelName":"…","displayName":"香港 01","countryCode":"HK","delay":123,"savedAt":…}
special_node_fallback = {同上}
```

- **写入**：`refreshSpecialNodes()` 每次拿到真实成员后更新（把现有的 `autoNode/autoNodeCountryCode/autoNodeDelay` 一并序列化）。
- **读取**：`ServerViewModel.init` 里先读缓存填充 `ServerData`，实时值到达后覆盖——内核离线时也显示"上次自动选择的成员+国旗+延迟"，图标右上可加一个小灰点表示"非实时"（可选，评审定）。
- 不新增网络请求，纯展示层记忆，改动集中在 `ServerViewModel` + `SessionStore`。

## 四、问题三：新增"离线"节点状态

### 4.1 语义定义（与现有状态的关系）

| 状态 | 含义 | 数据表现 |
|---|---|---|
| 速度（ms） | 节点正常，测速通过 | delay = 实测毫秒 |
| 超时 | 服务器**在**，但测速窗口内没回包（负载高/丢包/限速） | 现状 999 |
| **离线（新增）** | 服务器**不在了**：域名解析失败、连接被拒、路由不可达——节点后端已失效 | 新增 |
| 无值 | 从未测过 / 缓存过期 | delay = null（显示 `--`） |

另有一种"不存在"：节点从订阅里被删除——更新订阅后自然从列表消失，不属于本状态的处理范围。

### 4.2 技术约束（为什么现在做不了）

- 桥接层（`kernel-core/.../Clash.kt`）只有**组级** `healthCheck/healthCheckAll`，按节点测速不存在；`Proxy.delay` 是纯 Int，**失败原因在桥上就丢了**。mihomo 内部对 DNS 失败、连接拒绝、超时都只落到 delay=0。
- 因此"离线 vs 超时"的区分必须新增数据来源，两个途径：

### 4.3 方案设计

**数据模型先行**（两个途径共用）：

```kotlin
// 替代 Map<String, Int> 的缓存结构（SessionStore 新键，旧键读取兼容后废弃）
sealed interface NodeStatus {
    data class Alive(val delay: Int) : NodeStatus
    object Timeout : NodeStatus      // 在但不回包
    object Offline : NodeStatus      // 后端不存在
}
// 缓存条目：name → NodeStatus + testedAt；离线/超时也落盘（现状只存成功值）
// TTL 沿用 6h；订阅更新清空
```

**判定来源，二选一（推荐 a，b 作为过渡）：**

- **a. Go 桥扩展（与方案 A 同一次内核重编顺带做）**
  新增 `nativeUrlTest(name, timeout) → {delayMs, errorKind}`：桥内调 mihomo 按节点 URLTest，把错误串分类后返回枚举：
  - `context deadline exceeded` / 客户端超时 → **TIMEOUT**
  - `no such host` / `lookup …`（DNS 失败）→ **OFFLINE**
  - `connection refused` / `no route` / `network unreachable` → **OFFLINE**
  - 其余（TLS/HTTP 异常等）→ **TIMEOUT**（服务器大概率还在）
  `nodeLatencyStream` 改为逐节点走该接口（保留流式产出），失败节点获得精确状态。

- **b. 应用侧探测（纯 Kotlin 过渡版）**
  组级健康检查后收集 delay=0 的失败节点（数量少），app 对其 `host:port` 做直连探测：`ConnectivityManager` 绑定底层网络（绕开本机 VPN）→ DNS 解析失败/`ECONNREFUSED`/`EHOSTUNREACH` → **OFFLINE**；连接超时 → **TIMEOUT**。
  优点：不动内核；缺点：探测语义是"端口通"而非"代理可用"（端口通但协议挂了会误判为超时，可接受），实现要多一块网络代码。

**UI：**

- `ServerScreen.DelayText` → `NodeStatusText(status)`：绿色 `123ms` / 橙色"超时" / 红色"离线"；服务器页与首页"服务器"一行统一。
- 国旗行不受影响；离线节点保持正常排序（不做置灰下沉，避免列表跳动，评审可议）。

**缓存：**

- 状态随 §4.3 数据模型落盘，冷启动直接还原上次状态（离线/超时不再变成 `--`）；6h TTL 内不重测，进节点页手动测速强制刷新。

### 4.4 风险与边界

- **节点名映射**：内核名 ↔ 面板名经 `NodeNameResolver` 归一，缓存键用内核名，展示用面板名，订阅重名消解（`SanitizerProxyNames`）改名后旧缓存自然失效，无污染风险。
- **测速成本**：现状 healthCheckAll 已经全量打一遍，离线判定不新增测速流量（b 方案的 TCP 探测只针对失败节点）。
- **单元测试**：`NodeLatency` 已有虚拟时间单测范式，`NodeStatus` 分类逻辑（错误串→枚举）补纯函数单测即可。
